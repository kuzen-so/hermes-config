# AI内容生产系统

## 1. 系统架构

四层知识库，全部平铺在 `10-Inbox/` 下：

| 层级 | 文件夹 | 内容 | AI行为 |
|------|--------|------|--------|
| 语料库 | `voice/` | 用户说过的话、爆款段落、风格碎片 | 读全部，提炼《写作风格指南》 |
| 素材库 | `clip/` | 金句、概念、数据、拆解 | 按选题关键词grep搜索相关素材 |
| 内容工厂 | `idea/` `draft/` | 选题池、创作中、已发布 | 更新状态（idea→draft→pub） |
| 方法论 | `rule/` | 标题公式、结构框架、数据规律 | 读全部，套框架 |

## 2. 触发方式

用户说：
> "写公众号：AI副业4个月变现10万"
> "写小红书：我的第一个出海站"

AI自动执行：
1. `grep -r "AI副业\|变现" ~/Documents/Obsidian/10-Inbox/clip/` — 找相关素材
2. `cat ~/Documents/Obsidian/10-Inbox/voice/*.md` — 读风格
3. `cat ~/Documents/Obsidian/10-Inbox/rule/*.md` — 读框架
4. 按平台选框架（公众号/小红书）
5. 写初稿 → 存 `draft/idea-<选题>.md`
6. 标出AI味句子（营销体、替读者说话、指令语气、虚构数据、独立短句、加粗口号）

## 3. 用户动作

| 步骤 | 用户做什么 |
|------|-----------|
| 给选题 | 一句话，带平台 |
| 审初稿 | 看draft文件，标出不像自己的地方 |
| 改AI味 | 改标红的句子，或告诉AI"这句太AI了，换成..." |
| 确认发布 | 说"发"或"再改" |
| 数据复盘 | 发布后给数据（阅读/点赞/收藏），AI更新rule/ |

## 4. 去AI味检测清单

写完初稿自动跑一遍，命中标红：

- [ ] 营销体大词：赋能、闭环、打通、底层逻辑
- [ ] 替读者说话：「你可能觉得……」「很多人会问……」
- [ ] 指令语气：「记住」「一定要」「核心就一句话」
- [ ] 虚构数据：「90%的人不知道」
- [ ] 独立短句装戏剧感：一句话。一个词。成段。
- [ ] 加粗口号金句：真正厉害的人都在……

## 5. 平台框架差异

| 维度 | 公众号 | 小红书 |
|------|--------|--------|
| 定位 | 下沉市场/信息流/情绪 | 有目的搜索/解决生活具体问题 |
| 爆款公式 | "从0-1带你..." "用对X，瞬间提升" "突发/怎么办" | 具体产品名+反常识结论+≤20字 |
| 标题 | 硬数字+冲突+转折 | 产品名占搜索关键词，帮用户判断相关性 |
| 结构 | 痛点→方案→步骤→结果 | 具体问题→个人解法→经验分享 |
| 深度 | 拒绝深度，200-400=低，7000-14000=高 | 搜索场景，不深，靠精准命中问题 |

## 6. 数据复盘→方法论沉淀

每发一篇，用户给数据，AI更新 `rule/`：

```
输入：阅读量 X，点赞 Y，收藏 Z
输出：更新 rule/title-formula.md 或 rule/structure-pattern.md
```

规则从数据里长出来，不是拍脑袋。

## 7. 规则与流程的分工（新）

**用户明确的工作流：**

| 内容 | 位置 | 谁维护 |
|------|------|--------|
| 创作规则、爆款公式、平台策略 | **Obsidian 规则文档** | 用户 |
| 执行流程、步骤、工具调用 | **Skill** | 用户或 AI |

**运作方式：**
1. 用户说"加载 content-production-system"
2. AI 加载 skill（流程）
3. 执行中需要判断时，读 Obsidian 里的规则文档
4. 按规则执行

**关键原则：**
- Skill 只放**流程**（怎么做），不放**规则**（什么原则）
- 规则在 Obsidian，容量大、用户自己维护
- 记忆（MEMORY）不放创作规则，避免挤掉真正该记的偏好和纠正

**之前的问题：**
- 创作规则混在 MEMORY → 每轮注入 → AI 默认创作模式 → 说什么都往文章上靠
- 现在：规则在 Obsidian，按需读取；Skill 只加载流程

**用户触发边界：**
- 日常聊天 ≠ 内容生产
- 用户明确说"加载 skill"或"开始写"才进入创作模式
- 不主动假设用户要创作

## 8. 配图生成与验证

小红书/公众号文章常需配图。用户可能使用 nanobanana、Gemini、ComfyUI 等工具生成。

**生成后验证流程：**
1. 用户说"这是生成的图片"时，**不要仅凭系统附带的 image description 判断**
2. 系统 description 可能把文件占位符图标误当成实际内容
3. **必须**用 `vision_analyze` 检查本地文件实际内容
4. 确认是真实配图后，再给出评价

**常见错误：**
- 用户发了多张图，系统 description 显示"PNG 文件图标"
- 实际本地文件可能是正常生成的配图
- 不经 vision_analyze 验证就回复"这是文件图标不是配图" → 用户 frustration

**正确做法：**
```
用户：这是我生成的配图
→ ls 查看文件路径
→ vision_analyze 检查实际内容
→ 再评论
```

**陷阱1：语料库为空时写稿**
→ voice/ 里没有内容 → AI无法提炼风格 → 初稿AI味重
→ 解决：先攒20-30条语料，或从已发布的爆款文章里拆

**陷阱2：rule/ 里没有框架**
→ 第一次用时rule/为空 → AI不知道什么结构有效
→ 解决：先从已发布文章里提炼标题公式和结构，存进rule/

**陷阱3：素材库关键词搜索不到**
→ clip/ 里命名不规范 → grep搜不到
→ 解决：clip文件命名带关键词，如 `clip-bookmark-rate.md` `clip-ai-side-hustle.md`

**陷阱4：用户说"写"但没给平台**
→ 默认按公众号写，但用户可能想要小红书
→ 解决：反问"公众号还是小红书？"

**陷阱5：初稿太长**
→ 用户没给字数限制 → AI写2000字 → 用户嫌长
→ 解决：默认公众号800-1200字，小红书300-500字，除非用户另有要求

**陷阱6：强迫用户做事/用激将法**
→ 用户说"我不喜欢你这种敢不敢的语气，有点激将法的感觉"
→ 用户要的是"找回自己"，不是被推着走
→ 解决：不问"敢不敢""能不能""要不要"，只提供选项，不施压
→ 用户想发就发，不想发就不发，不需要批准或激将
→ **核心原则**：用户要的是被听见，不是被解决

**陷阱7：把日记和语料库分开**
→ 用户问"想法看法记录在哪"，回答"日记里"即可
→ 语料库 = 日记中"有情绪张力的片段"
→ 不需要第二个文档，不需要分类、链接、维护系统
→ 写的时候心里有"这句有刺"就够了

**陷阱9：忘记小红书标题≤20字约束**
→ 用户已明确告知多次，仍生成超长标题
→ 解决：生成小红书标题时主动数字数，>20字立即压缩
→ 优先保留：产品名（英文占字符少）+ 核心动词 + 结果
→ 用户说"你的问题总是在强迫我去做事"
→ 用户卡住时，可能需要的是梳理思路，不是下一步行动
→ 判断信号：用户连续多轮在谈感受/困惑/回忆，而非问"怎么做"
→ 此时应停止给下一步，只听和回应
→ 区分"要突破卡住"和"要被听见"两种需求

## 8. 文件操作纪律

- 只操作用户明确提到的文件
- 删除文件先进回收站（`~/.Trash/`），不直接`rm -rf`
- 修改文件前确认路径，不碰未提及的文件
- 批量移动时先`cp`再`rm`，或`mv`到可见位置
