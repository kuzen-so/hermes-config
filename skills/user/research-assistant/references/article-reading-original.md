# 文章阅读工作流（Reference — 原始完整版）

## 一、判断输入类型

| 输入类型 | 识别方式 | 提取工具 |
|---------|---------|---------|
| 网页 URL | 以 http:// 或 https:// 开头 | `browser_navigate` + `browser_snapshot`（动态内容）或 `web_extract`（静态） |
| 本地 Markdown/TXT | 以 `~` 或 `/` 开头的文件路径 | `read_file` |
| PDF | 以 `.pdf` 结尾 | `pymupdf` 或 `ocr-and-documents` skill |
| 图片中的文字 | 以 `.png`/`.jpg`/`.webp` 结尾 | `vision_analyze` OCR |

**URL 优先级：**
1. 先尝试 `browser_navigate` 加载完整页面，用 `browser_snapshot(full=true)` 拿到渲染后的内容
2. 如果被反爬或加载失败，退而使用 `web_extract`
3. 微信公众号文章通常需要 browser 模式

## 二、内容提取原则

**不要全文转录。** 只拿三样东西：
1. **能填补你认知缺口的观点**
2. **能当作写作素材的案例/数据/故事**
3. **能当金句用的表达**

剩下的都是冗余。

## 三、笔记结构（默认输出格式）

```markdown
---
title: "文章标题"
source: "URL或文件路径"
date: "YYYY-MM-DD"
type: "article"
tags: []
---

# 一句话总结
（用你的口气重述核心论点，不是拷贝原文）

# 核心观点分析
（拆解作者到底在主张什么，不是复述原文，而是提炼其底层逻辑）

# 解决了什么问题
（这篇文章针对什么痛点、现状或矛盾而写，回答"为什么现在需要这个观点"）

# 核心要点
1. 点一：...
2. 点二：...
3. 点三：...
（每条不超过 3 行，口语化，去AI化）

# 观点可行性评估
（站得住脚吗？证据是否充分？前提是否成立？有什么限制条件或反例？适用范围是什么？）

# 可用素材
- 案例：...
- 数据：...
- 故事：...
- 金句：...

# 我的启发
（留空，供用户自己填写）
```

## 四、保存位置

**默认：**
- 如果用户没有特殊说明，保存到 `~/Documents/Obsidian/01-Inbox/Readings/`
- 文件名格式：`YYYY-MM-DD-文章标题简写.md`

**若用户有固定素材库：**
- 询问用户保存到哪里，再执行

**若用户只想看摘要不想存：**
- 直接返回结果，不写文件

## 五、风格约束

1. **去AI化** — 禁用 "首先/其次/再次/最后/总之/不得不说"等词
2. **口语化** — 像跟朋友转述一样
3. **结构化** — 用列表和短段落，不要大段落密集文字
4. **二人称**— 笔记是写给"你"看的，而不是第三人称报告

## 六、特殊场景处理

**微信公众号文章：**
- 通常有声明、广告、导语等包装，需要 browser 加载完整内容后手动过滤
- 找出"作者真正想说的那句话"，剥离营销包装

**英文文章：**
- 摘要部分用中文输出
- 金句/专有名词保留英文原文，后面抬中文解释

**视频文章（YouTube/B站）：**
- 交给 `youtube-content` skill 处理，本 skill 不覆盖视频

## 七、处理流程

1. 用户提供文章
2. 判断类型 → 选择提取工具
3. 抽取核心内容（不超过原文 30%）
4. 分析：核心观点 → 解决问题 → 可行性评估
5. 按"笔记结构"重构
6. 询问保存位置（如果用户没指定）
7. 写入文件或返回摘要

## 八、常见错误

- ⚠️ **全文转录** — 用户要的是"精华"，不是"复制粘贴"
- ⚠️ **混淆观点与事实** — 明确区分"作者说了什么"和"作者用什么证据支撑"
- ⚠️ **漏掉可用素材** — 特别是数据、案例、故事，这些是写作时最缺的
